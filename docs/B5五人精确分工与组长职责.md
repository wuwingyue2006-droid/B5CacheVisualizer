# B5 五人精确分工与组长职责

> 项目：多级 Cache 映射与替换算法可视化演示系统
> 成员代号：A、B、C、D、E
> 技术组长：成员 A

## 一、谁是组长

```text
成员 A = 技术组长 + Core 负责人 + 系统集成人
```

A 不只是普通的 Core 开发成员，还负责：

- 总体架构和模块边界；
- 公共数据结构与接口；
- Git 分支和 PR 规则；
- B–E 的 PR 检查；
- 跨模块冲突处理；
- 全量测试和最终发布；
- 稳定版本从 `dev` 进入 `main`。

因此 A 的工作量和责任高于普通成员是正常的。

## 二、五人分工总表

| 代号 | 身份 | 负责模块 | 个人分支 | 主要目录 |
|---|---|---|---|---|
| A | 技术组长 | Core、L1/L2 调度、公共接口、系统集成 | `feature-core` | `src/core/` |
| B | 模块成员 | 地址解析与 Mapping | `feature-mapping` | `src/mapping/` |
| C | 模块成员 | FIFO/LRU Replacement | `feature-replacement` | `src/replacement/` |
| D | 模块成员 | MFC UI 与动态可视化 | `feature-ui` | `B5CacheVisualizer/` |
| E | 模块成员 | Trace、Statistics、测试数据 | `feature-statistics` | `src/statistics/`、`src/trace/` |

个人任务卡：

```text
A → docs/tasks/A-core.md
B → docs/tasks/B-mapping.md
C → docs/tasks/C-replacement.md
D → docs/tasks/D-ui.md
E → docs/tasks/E-statistics.md
```

本文档用于全组理解总体边界。开始开发时仍须读取自己的任务卡、`AGENTS.md`、`docs/INTERFACES.md` 和 `docs/OWNERSHIP.md`。

## 三、模块连接关系

```text
                    D：MFC UI
              输入、按钮、表格、高亮
                         │
                         ▼
                 A：CacheSimulator
                L1/L2 调度与集成
                  │      │      │
                  ▼      ▼      ▼
          B：Mapping  C：Replacement  E：Statistics
                                          ▲
                                          │
                                      E：Trace
```

固定依赖原则：

- D 只读取输入、调用核心、展示结果，不重新实现算法；
- A 统一调用 B、C、E，不复制其实现；
- B 只负责地址映射，不选择 victim；
- C 只负责 FIFO/LRU，不判断 set/tag；
- E 负责 Trace 和统计，不控制 Cache Line；
- 公共类型由 A 统一控制。

## 四、A：技术组长、Core 与系统集成

### 4.1 开发前职责

A 负责制定和维护：

- 仓库文件结构；
- 类与模块依赖；
- 公共数据结构；
- `CacheSimulator` 对外接口；
- 文件归属；
- Git 分支和 PR 规则；
- 测试与验收标准；
- 模块合入顺序。

### 4.2 Core 开发职责

A 负责：

- `CacheSimulator::Access()` 和 `Run()`；
- L1 查询；
- L1 Miss 后访问 L2；
- L2 Miss 后模拟主存；
- L1/L2 填充顺序；
- 写访问与 dirty 状态；
- Reset；
- 配置合法性；
- `AccessResult` 完整性；
- Mapping、Replacement、Statistics 的统一调用。

主要允许修改：

```text
src/core/CacheLevel.h
src/core/CacheLevel.cpp
src/core/CacheSimulator.h
src/core/CacheSimulator.cpp
B5CacheCoreTests/CoreTests.cpp
```

### 4.3 组长专属职责

A 必须：

1. 收集 B–E 的阶段上传报告；
2. 检查 PR 的 base 是否为 `dev`；
3. 检查成员是否修改了越界文件；
4. 审批公共接口修改；
5. 检查编译和测试证据；
6. 决定 PR 是否合入；
7. 处理 merge conflict；
8. 每合入一个模块后重新运行完整测试；
9. 维护 TODO 和已知问题；
10. 组织跨电脑运行测试；
11. 整理 Release 和最终演示；
12. 在稳定后组织 `dev → main`。

### 4.4 A 不应该做什么

- 不替 B 重写 Mapping；
- 不替 C 重写 FIFO/LRU；
- 不把 D 的 UI 逻辑写进 Core；
- 不替 E 复制 Trace/Statistics；
- 不未经检查一次合入所有人的分支；
- 不把开发中的 `dev` 直接当最终版本。

### 4.5 A 的完成标准

- [ ] L1/L2 主流程正确；
- [ ] 三种 Mapping 可通过统一接口使用；
- [ ] FIFO/LRU 可通过统一接口使用；
- [ ] Statistics 每次访问只记录一次；
- [ ] Trace 和 UI 能通过公共接口工作；
- [ ] Reset 和异常配置有测试；
- [ ] B–E 的 PR 全部经过检查；
- [ ] 自动测试和 UI 测试通过；
- [ ] 最终 `dev → main` 有明确版本记录。

## 五、B：地址解析与 Mapping

### 5.1 负责内容

B 负责：

- Block Number 关系；
- Tag；
- Index / Set Index；
- Offset 的解释与验证；
- Direct Mapping；
- Fully Associative；
- Set Associative；
- lineCount、associativity、setCount 合法性；
- Mapping 单元测试。

当前固定接口以 `blockNumber` 作为输入，因此地址到 `blockNumber` 的除法由 Core 完成；B 保证 set/tag 公式正确。如果需要向 UI 新增 offset 或二进制字段，先向 A 申请公共接口修改。

主要允许修改：

```text

src/mapping/MappingStrategies.cpp
B5CacheCoreTests/MappingTests.cpp
```

### 5.2 不负责

- 不选择 victim；
- 不维护 Hit/Miss；
- 不操作 MFC；
- 不修改 Core 来掩盖错误公式。

### 5.3 输入输出

```text
输入：blockNumber、lineCount、associativity
输出：setIndex、tag、setCount
```

### 5.4 完成标准

- [ ] Direct/Fully/Set 三种映射正确；
- [ ] 非法输入明确报错；

- [ ] 不越界修改其他模块；
- [ ] 完整测试通过。

主要允许修改：

### 6.4 完成标准

## 十、相对原分工建议的三处收紧

### 10.1 CacheLine/CacheSet 由 A 统一控制

C 可以提出字段需求，但公共结构由 A 修改，避免 A/C 同时改公共头文件。

### 10.2 E 提供图表数据，D 绘制 MFC 图表

图表控件属于 UI，所以 E 保证数据正确，D 负责画面和刷新，两人通过 `StatisticsSnapshot` 连接。

### 10.3 复杂合并交给 A

B–E 只负责 commit、push 和创建 `feature-* → dev` PR。A 负责审核、冲突处理和合入。

这些调整是为了减少公共文件冲突，不是减少任何人的工作量。

## 十一、开发与合入顺序

五人可以并行开发，建议 PR 合入顺序：

```text
1. B：Mapping
2. C：Replacement
3. E：Statistics / Trace
4. A：Core 集成
5. D：UI 最终联调
```

D 可以提前搭界面，但最后连接完整模块最稳妥。每合入一个 PR，A 都要在最新 `dev` 运行完整测试。

## 十二、阶段安排

### 阶段 0：接入和统一设计

- 全员 clone 最新 `dev`；
- A 确认接口、分支和任务卡；
- 每人创建唯一个人分支；
- 每个 AI 读取本地规范。

### 阶段 1：纯 C++ MVP

- B 完成三种 Mapping；
- C 完成 FIFO/LRU；
- E 完成基础 Statistics/Trace；
- A 保证控制台核心流程可运行。

### 阶段 2：UI 与测试并行

- D 完成配置、Step、Run All、Grid；
- E 扩展异常输入和固定测试；
- A 开始阶段集成。

### 阶段 3：L1/L2 联调

- A 核对多级流程；
- D 显示两级 Cache；
- E 核对统计；
- B/C 处理策略边界问题。

### 阶段 4：全组验收

- 全部 PR 合入 `dev`；
- 自动测试和 UI 清单通过；
- 跨电脑运行；
- 固定演示 Trace 通过。

### 阶段 5：最终发布

- A 整理 Release；
- `dev → main`；
- 记录最终 commit；
- 全员提交本人模块报告和 AI 使用记录。
